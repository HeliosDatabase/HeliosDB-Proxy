# HeliosProxy 1.7.0 — Transaction Replay that checks its own work

*2026-09-11 · `heliosdb-proxy` 1.7.0 on crates.io*

A proxy that replays your transaction onto a new database after the old one dies is
making a promise: *what you already saw is still true*. HeliosProxy 1.7.0 is the
release where that promise stops being an assumption and becomes something the proxy
verifies, statement by statement — and where it says so plainly when it cannot.

This closes a six-item correctness series that began with an adversarial audit of
1.6.0. Every defect that audit found in Transaction Replay is fixed and shipped.

---

## What Transaction Replay does

A client connects to HeliosProxy instead of to PostgreSQL. When the backend serving
that session dies — crash, failover, network partition, a `pg_terminate_backend` — the
proxy keeps the client connection open, finds a healthy primary, re-establishes the
session on it, and resumes. `tr_mode` selects how far that goes, and each level
includes the one before it:

| `tr_mode` | What survives a backend failure |
|---|---|
| `none` | Nothing. One error, connection closed. |
| `session` *(default)* | The connection and its session state. A statement that never reached the dead backend is re-run. |
| `select` | Plus: an interrupted read is re-executed, when that read is provably side-effect-free. |
| `transaction` | Plus: an uncommitted transaction is replayed from its `BEGIN` on the new primary and the interrupted statement re-run inside it. |

It needs no cargo feature and no application change — any PostgreSQL-wire client, any
PG-wire backend. The `ha-tr` feature is something else: a write journal and the
operator-driven `/api/replay` and `/api/shadow` endpoints.

**Proven, not asserted.** The base path was established at 1.6.0 by a 77-check live
failover battery against real PostgreSQL — a client holds an open transaction, the
backend is killed under it, and the harness asserts what the client received, in which
order, and what the database contains afterward. Every release since has additionally
had to pass the commit-outcome and streaming suites described below, which is how the
defects this release closes were found in the first place.

## The fixes

Each of these was a real defect with a reproducing test that failed before the fix and
passes after.

**TR-01 — Commit boundaries are now lexed, not guessed.** Deciding whether a statement
might have committed was pattern-matching that could be fooled by a comment, a quoted
string, a dollar-quoted body, or several statements in one Query message. A bounded
PostgreSQL-aware scan now classifies every commit boundary — including `PREPARE
TRANSACTION` / `COMMIT PREPARED` and every `Execute` in a pipelined batch. Against a
live PostgreSQL commit-outcome suite, the pre-fix binary failed 4 of 7 cases; it now
passes all 7.

**TR-02 — A result the client already saw is never extended.** The fault context now
carries how much of a response has actually reached the client. Once any part of a
result is visible, recovery reports a clean failure instead of appending rows from a
second execution to the first one's output. The pre-fix binary failed 12 of 13 live
streaming cases; it now passes all 13. A review pass found one uncovered path — the
idle backend-watch relay could publish a chunk that ended mid-frame — and that relay
now forwards only complete protocol frames.

**TR-03 — "It's a SELECT" is not a licence to run it twice.** Re-executing an
interrupted read used to be decided by the leading keyword. A `SELECT` can call
`nextval()`, `pg_notify()`, `set_config()`, an advisory lock, or any user-defined
function with arbitrary effects. Replay now scans every function call in the statement
and re-executes only when each one is a PostgreSQL built-in known to be
side-effect-free — or a name you added to the new `tr_read_functions`. Anything else
is opaque: the client gets `08007` and the statement is never run a second time.

**TR-04 — Session state is restored the way PostgreSQL actually behaves.** A `SET`
inside a transaction is not permanent until that transaction commits, and
`ROLLBACK TO SAVEPOINT` undoes the ones made after the savepoint. Restore now models
exactly that: operations are deferred to commit, savepoint-scoped on rollback, and
keyed by variable name so repeating a `SET` reuses its slot instead of consuming
another. A rolled-back `RESET ALL` no longer wipes the restore set. When the tracked
state exceeds its cap, the failover is refused with `08006` rather than silently
re-homing a session with half its settings.

**TR-05 — A failed write is not proof the write never happened.** A `write_all` of a
pipelined batch that fails partway does not mean the earlier `Execute` messages never
ran. Delivery progress is now tracked at byte and frame granularity, and uncertain
prefixes are classified conservatively. A connect failure before any byte was sent
remains eligible for the safe retry path — uncertainty is not treated as a blanket
refusal.

**TR-06 — Replay verifies its own results, and the recovery has one clock.** While a
transaction is recorded, each statement's response frames are hashed in order into a
bounded digest. During replay the replacement backend's responses are hashed the same
way. Any divergence rolls the replay back and returns `40001` instead of continuing a
transaction on top of rows the client never observed. Transactions pinned to a
`SERIALIZABLE` or `REPEATABLE READ` snapshot are never replayed — no replacement
backend can reproduce that snapshot. And `write_timeout_secs` is now a single deadline
covering the whole recovery: waiting for a primary, connecting, authenticating,
restoring session state and replaying. Previously each phase had its own timeout and
they could add up well past the configured value.

**H-07 — Every backend frame is bounded.** A malformed length below the 4-byte protocol
minimum used to leave a relay waiting for bytes that could never complete the frame; an
absurd advertised length grew a buffer toward the requested size. Every streaming relay
now validates each frame header against `[limits] max_backend_frame_bytes` and closes
the offending backend. A companion `backend_response_timeout_secs` bounds a response as
a whole, which a per-read timeout can never do against a backend trickling bytes.

## How it was tested

Correctness claims about failover are worth exactly as much as the failures you
actually injected. What ran against this release:

- **Live PostgreSQL commit-outcome suite (7 cases).** Real PostgreSQL 18.4 in a
  disposable container; the connection is destroyed at the moment a `COMMIT` is in
  flight, and the suite then asserts against the database's real state whether the
  client's report was correct. The pre-fix binary failed 4.
- **Live streaming suite (13 cases).** Faults during large result sets, across `Flush`
  chunks, mid-`DataRow`, after `CommandComplete`. Asserts that no client ever sees a
  duplicated row or a second protocol completion. The pre-fix binary failed 12.
- **Synthetic boundary harness (26 cases).** Commit-boundary classification against
  comments, quoted and dollar-quoted text, multi-statement strings, backslash escapes
  under both `standard_conforming_strings` readings, `ROLLBACK; <DML>`, savepoint
  stacks, and GUC cap behavior.
- **Deterministic partial-writer.** A writer that fails after *every* byte offset, plus
  timeouts and zero-length writes, confirming no offset can produce a duplicate
  committed write.
- **Adversarial review.** The fix set was read by three independent reviewers, one per
  lens — commit classification, response publication, delivery safety — before merge.
  That is how the mid-frame publication path was caught.
- **One recommendation was rejected.** A reviewer proposed not closing the session after
  a published `CommandComplete`. It reads like an availability win, but injecting an
  error after a statement the backend actually finished tells the client a completed
  `INSERT` failed — and a client that retries it double-applies. The harness caught the
  regression when it was tried.
- **Regression attribution by reconstruction.** Before accepting the review fixes, the
  pre-review tree was rebuilt in a scratch worktree and run through the same harness, so
  "did this change break that?" was answered with data rather than reasoning.
- **Full gate matrix on the release commit.** `clippy -D warnings` across four feature
  profiles; 432 / 518 / 1726 / 1727 tests on default, `ha-tr`, `all-features` and
  `all-features,postgres-topology`, zero failures; MSRV 1.86 with a locked dependency
  graph; benchmark compile; `--no-default-features` check.

## What it still refuses to do

Transparent recovery is the goal; a clear error is the fallback, and a wrong answer is
never acceptable. The proxy declines, and says why, when:

- a `COMMIT`'s outcome is genuinely unknown — it is never retried (`08007`, with
  guidance to verify);
- part of a response already reached the client — the session closes rather than
  concatenate a second result;
- the transaction ran at `SERIALIZABLE` or `REPEATABLE READ`;
- a response was too large to have been digested within `tr_max_observation_bytes`, so
  it cannot be verified;
- an interrupted read calls anything outside the side-effect-free set;
- tracked session state exceeded its cap (`08006`).

Known limits, stated plainly: prepared statements, session temp tables and open cursors
are **not** restored across a failover, and `SET`s issued through the extended protocol
are not tracked. Replay does not make `now()`, `random()` or a `RETURNING` serial
reproduce their first values — verification catches divergent *results*, it does not
create determinism. The `ha-tr` journal behind `/api/replay` is in-memory and
best-effort; hardening it into a durable, ordered, recovery-grade log is the next item
in this series.

## New configuration

| Key | Default | Purpose |
|---|---|---|
| `tr_read_functions` | `[]` | Extra function names an interrupted read may call and still be re-executed. |
| `[limits] tr_max_observation_bytes` | 1 MiB | Per-statement budget for the digest replay is verified against. |
| `[limits] backend_response_timeout_secs` | `0` (off) | Whole-response deadline for a slow-dripping backend. |
| `[limits] max_backend_frame_bytes` | 100 MiB | Ceiling on any single backend protocol frame. |

`write_timeout_secs` keeps its name and default (30s) but now bounds the entire
recovery rather than only the wait for a primary.

## Upgrading

Drop-in from 1.6.x — no configuration changes are required, and the new limits have
safe defaults. Sessions using `tr_mode = "transaction"` will see replay refused in cases
where it previously proceeded (snapshot-pinned transactions, unverifiable responses);
that is the point of the release, and each refusal carries a specific SQLSTATE.

```toml
tr_enabled = true
tr_mode = "transaction"
write_timeout_secs = 30
```
