# HeliosProxy 3.1.0

*2026-11-26 · `heliosdb-proxy` 3.1.0 on [crates.io](https://crates.io/crates/heliosdb-proxy) ·
prebuilt binaries and checksums on this GitHub release · image
`ghcr.io/heliosdatabase/hdb-heliosdb-proxy:3.1.0`*

HeliosProxy 3.1.0 makes the connection pool configurable for real and gives tenants their
own isolation and pools. It is non-breaking: every configuration that starts on 3.0 starts
on 3.1, every default keeps 3.0's behaviour, and the Rust library API only gains items
(some old ones are deprecated and keep working).

## What's new

### The pool keys act

The `[pool]` and `[pool_mode]` keys were parsed in 3.0 but not used. In 3.1 the data path
reads them:

- **Connection caps.** `[pool] max_connections` caps each node's backend connections; a
  `[[nodes]] max_connections` overrides it per node.
- **Warm connections.** `[pool] min_connections` and `[pool_mode] min_idle` keep
  connections open and parked ahead of use. The proxy opens them with its own credential
  (`[auth] mode = "scram"` with a plaintext `auth_file` entry) or against a trust
  backend. An identity it holds no password for is skipped, with one warning.
- **Idle and lifetime limits.** `idle_timeout_secs` and `max_lifetime_secs` close idle and
  old pooled connections, never one in use.
- **Acquire deadline.** `[pool_mode] acquire_timeout_secs` bounds the whole wait for a
  backend connection. A request that cannot get one within the proxy's bounds is answered
  with SQLSTATE 53300 and its session goes on.
- **Liveness probe.** `test_on_acquire = false` skips the probe and redials once when the
  leased socket turns out dead.
- **Prepared statements in pooled modes.** `prepared_statement_mode` acts in transaction
  and statement pooling: `track` (and the default `named`) re-prepares SQL `PREPARE`
  statements on another connection before an `EXECUTE`; `disable` refuses them with
  0A000.
- **Slow standbys.** `[load_balancer] latency_threshold_ms` holds slow standbys out of
  read offload.
- **Real reporting.** `GET /pools` reports every node's real connections, and `/metrics`,
  `/metrics/prometheus` and `/api/stats` carry the pool counters
  (`heliosdb_proxy_pool_*`).

### Tenant isolation and per-tenant pools

The new `[multi_tenancy] tenant_settings` list sets, for each tenant:

- its `isolation`: `row` (as before), `schema`, `database` or `branch`;
- its schema, database or branch, and its caps;
- `pool_max_idle` and `pool_max_connections`, which give the tenant its own capped pool.

A session is pinned to its tenant when it connects. Its startup parameters are rewritten
once (`search_path`, database, or `<db>@<branch>`), and `[[hba]]` is checked again
against the database it really gets. `lock_search_path` refuses statements that change
the search path. `/metrics` and `/api/stats` report each tenant pool's dials, checkouts,
waits and refusals (`heliosdb_proxy_tenant_pool_*`). The existing `tenants` list of ids
keeps working.

## Upgrading

Upgrading is a binary or image swap, but review any pool keys your configuration sets:
they now have an effect. In particular, an explicit `prepared_statement_mode = "disable"`
now refuses prepared statements in transaction and statement pooling. Values 3.0 accepted
but that make no sense (for example `acquire_timeout_secs = 0`) are warned about and read
safely instead of refused. Details are in the changelog's upgrade notes.

## Measurements

User-path gate against 3.0.1 (pgbench, live PostgreSQL 18 backend, 12 interleaved
passes, session and transaction pooling at 16 and 64 clients):

- Tenancy on: every cell within the 3 % budget; mean throughput +1.8 %, mean p99 −2.1 %.
- Simple protocol: mean throughput −0.3 %, mean p99 −1.0 %; one session-pooling cell had
  a 3.3 % higher p99.
- Prepared protocol: mean throughput +0.0 %, mean p99 +0.6 %; one session-pooling cell had
  a 6.3 % higher p99, the same cell that varied between runs in 3.0.0 and 3.0.1.
