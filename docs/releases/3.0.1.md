# HeliosProxy 3.0.1

*2026-11-23 · `heliosdb-proxy` 3.0.1 on [crates.io](https://crates.io/crates/heliosdb-proxy) ·
prebuilt binaries and checksums on this GitHub release · image
`ghcr.io/heliosdatabase/hdb-heliosdb-proxy:3.0.1`*

HeliosProxy 3.0.1 is a performance patch for 3.0.0. It lowers the proxy's CPU cost per
statement on the relay path. Nothing else changes: the configuration file, command-line
flags, admin API, wire-protocol behaviour and the Rust library API are the same as in
3.0.0. Upgrading is a binary or image swap.

## What changed

- **Backend connection lookup without hashing.** A session keeps its backend connections
  (usually one to three) in a small list searched by node address instead of a hashed map.
  The relay looks a connection up several times per statement, so this removes several
  hash computations from every statement.
- **No lock for the in-flight slot when none is held.** The per-request release of the
  `[rate_limit] max_concurrent` slot now checks a flag first and only takes the lock when
  the session actually holds a slot. Without `max_concurrent` it never does.
- **Journal source identity resolved once per session.** The transaction journal records
  who sent each transaction (client address, user, database, tenant). That identity was
  rebuilt for every journaled statement; it is now resolved once per session and only
  the backend address is compared each time.

## Measurements

pgbench simple-update over the simple protocol, session pooling, 16 clients, 12 rotating
rounds, sampled CPU profile of the proxy process:

| Build | Proxy CPU samples per 1,000 transactions |
|---|---:|
| 2.2.0 | 3,150 |
| 3.0.0 | 3,367 |
| 3.0.1 | 3,229 (4.1 % less than 3.0.0) |

User-path gate against 2.2.0 (pgbench, live PostgreSQL 18 backend, 12 interleaved passes,
session and transaction pooling at 16 and 64 clients):

- Simple protocol: every committed-write cell within the 3 % budget; the session/16 cell
  that was 2.7 % slower with a 4.5 % higher p99 in 3.0.0 is now level (TPS +0.6 %, p99
  −1.7 %).
- Cache on (simple and prepared), transaction replay in transaction mode: within budget.
- Prepared protocol and tenancy: TPS within budget in every cell; p99 over the 3 % budget
  in three cells (+3.2 % to +5.0 %), the same cells as in the 3.0.0 runs, which passed
  and failed between repeated runs.

Criterion micro-benchmarks against 3.0.0: mean change +0.34 % across 170 cases; the
slower cases are all in benchmark binaries whose function bodies are identical to 3.0.0
(code layout only).
