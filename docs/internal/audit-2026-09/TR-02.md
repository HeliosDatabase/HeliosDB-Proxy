# TR-02 implementation — response publication boundaries

The working-tree relay carries client-visible response progress into backend fault
recovery. A failure after complete row frames have been sent cannot authorize a
second execution whose rows would be appended to the original result. Recovery
returns one error at that frame boundary. If CommandComplete or ErrorResponse has
already been published, it closes the connection without adding a second terminal
response. These decisions also apply when the replacement backend fails.

Flush output is relayed as raw bytes and can end inside a frame. A session now
remembers dispatch across Flush chunks independently of transaction recording and
the selected replay mode. A failed later chunk cannot establish that earlier
Executes were unsent. Such a failure closes the socket without injecting protocol
bytes into a potentially incomplete frame. Flush and backend-watch client writes
use the existing client-write timeout.

The capture path used by query-cache and edge-proxy retains the same progress even
after an oversized response has caused cache capture to be abandoned. Cache capture
is not a replay-publication buffer: it still streams rows immediately.

## Verification in progress

The Rust tests exercise the decision guard and socket relay with zero output, row
prefixes, CommandComplete and ErrorResponse, including the cache-capture path when
compiled. The daemon fault probe adds large rows, a reader consuming 1 KiB per read
with a 1 ms delay, extended cycles, raw Flush fragments, and all four replay modes.
Its assertions require the expected original row count, no replacement query, no
duplicate result or terminal frames, and an unchanged incomplete tail on close.

These tests and this implementation are not part of the frozen TR-01/TR-05
candidate. Their results must be recorded separately with the tested binary hash.

The real PostgreSQL fixture now accepts `--suite stream`. Its thirteen cases publish
exact PostgreSQL row prefixes, CommandComplete, ErrorResponse, or a partial frame,
then close the route. It includes a 64 KiB row with a slow reader, extended
Flush/Sync, cold/warm unnamed Parse optimization, and all four replay modes. It runs against the original binary as a
negative control before the candidate; the container retains the commit suite's
private data, loopback binding and resource limits. Results are pending.

TR-02 remains open. Optional bounded buffering for eligible small reads, measured
first-row latency and memory, and passing real PostgreSQL streaming-client evidence
are still required. SQL replay eligibility is tracked separately in
TR-03; backend frame validation and slow-drip bounds are tracked in H-07.
