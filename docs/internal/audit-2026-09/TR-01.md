# TR-01 implementation — commit outcome safeguards

This change strengthens live `tr_mode` replay on default, no-default and `ha-tr`
builds. The original audit evidence describes the unmodified 1.6.0 baseline;
implementation evidence is stored separately with `tr01-` filenames.

## Behavior

- A lexical guard recognizes COMMIT, END and PREPARE TRANSACTION through nested
  block comments, line comments and statement separators. It skips quoted tokens,
  including dollar quotes and non-ASCII dollar tags. Unterminated tokens and
  backslash-escaped strings refuse uncertain-outcome replay conservatively because
  session string-escaping settings are not tracked. Existing read eligibility
  restrictions remain; this change does not resolve TR-03 volatility policy.
- Extended recovery checks every Execute against its Bind-time statement identity,
  including unnamed statements and held Parse optimization. Bind parameters and
  format codes remain raw bytes. Replacing a statement after Bind does not change
  the bound portal's safety classification.
- Per-batch statement/portal inspection borrows names and is capped by existing
  `[limits] max_prepared_statements`. Exhaustion, incomplete frame headers/names and unresolved
  references refuse replay. The common unnamed shape allocates no statement/portal
  maps. The normal autocommit bookkeeping path skips this work.
- A successful batch containing COMMIT followed by BEGIN (or AND CHAIN) cannot
  retain and later replay the earlier committed transaction's history. Such a
  history becomes non-replayable until the transaction ends.
- `08007` now tells the client to verify the database outcome before retrying;
  it no longer tells the client the possibly committed transaction was aborted.

The lexical guard follows PostgreSQL's [lexical structure](https://www.postgresql.org/docs/current/sql-syntax-lexical.html).
Statement/portal identity and batching follow the [extended query protocol](https://www.postgresql.org/docs/current/protocol-flow.html).
This is a conservative lexical safety guard, not a full SQL validator.

## Deliberate limitations and remaining acceptance work

The routing registry is not an acknowledged, versioned statement/portal registry.
An Execute whose Bind or Parse is from an earlier completed cycle is therefore
opaque to recovery. Normal execution continues; on an uncertain outcome it returns
`08007`, and an explicit transaction containing opaque work cannot be transparently
replayed. Acknowledged cross-cycle identity remains a TR-01 follow-up.

The September 9 working-tree follow-up retains later held Parse messages at their
original positions between Flush chunks, including when the first Parse was not
held. It also retains a bounded BEGIN/Flush prefix while the last ReadyForQuery
still says Idle; losing that prefix must never let replayed DML run outside its
transaction. A recording cap exceeded before Sync, or a simple Query interrupting
the recorded extended cycle, makes the resulting transaction non-replayable.
Open-cycle bytes and statement admission are checked on each Flush. The original
TR-01 frozen candidate does not include these changes; the queued TR-02 candidate
includes them and four focused recorder tests, including recovery of the recording
budget after an oversized idle cycle finishes.

The companion [TR-05 fix](TR-05.md) preserves uncertainty for partially delivered
extended batches and tests failure at every byte offset of BEGIN/DML/COMMIT/Sync.
TR-02 streaming progress, TR-03 volatile expressions,
and TR-04 session restoration also remain open. No HA/promotion or multi-region
guarantee is established by these tests.

## Reproductions

The focused synthetic suite uses no database:

```sh
python3 scripts/regress/tr-boundary-test.py target/debug/heliosdb-proxy \
  --case plain_commit_unknown --case commented_commit_unknown \
  --case extended_commit_unknown --case transaction_replay_control --case extended_replay_control
```

The real-PG acceptance fixture starts and removes its own loopback-only Docker
container from the locally installed `postgres:18.4-bookworm` image. It caps memory
at 768 MiB, CPUs at one and processes at 64, with a private 256 MiB tmpfs. It uses no
existing service or host data directory. Run it under the fleet build lock, outside
benchmark measurements:

```sh
python3 tests/integration/tr_commit_outcome.py target/debug/heliosdb-proxy
```

It forwards unchanged protocol frames, waits for PostgreSQL to finish COMMIT or
PREPARE TRANSACTION and return ReadyForQuery, then discards that response and
closes the route. Assertions check the client's SQLSTATE, SQL dispatched to the
replacement route and committed ledger rows. PREPARE outcomes are inspected and
explicitly committed by the fixture before counting the ledger. This demonstrates
transaction execution before response loss; the tmpfs fixture does not test storage
power-loss durability, replication or promotion.

## Validation results

The original frozen candidate passed default, `ha-tr`, `all-features`,
`all-features,postgres-topology`, and no-default test commands. It passed the four
required clippy configurations and Rust 1.86 MSRV check. Five focused daemon probes
passed in default, all-features/postgres-topology, and no-default binaries. All
seven disposable PostgreSQL outcome cases passed; the original binary failed four.
Evidence is under `evidence/tr01-*.json`. All 107 benchmark measurements completed;
the performance gate remains open because individual benchmark regressions require
investigation (see `evidence/tr01-benchmarks.json` and `PROGRESS.md`).

These results do not validate the September 9 follow-ups or complete TR-01's
outstanding acknowledged-identity work.

## Remaining identity implementation contract

Recovery must not seed its classifier directly from the current routing registry:
that registry is overwritten when a frontend Parse arrives, before PostgreSQL
acknowledges it. A rejected replacement Parse can leave the previous definition
alive on PostgreSQL while the registry contains different SQL.

- Keep bounded, immutable acknowledged Parse generations separately from pending
  frontend changes. Inspect a batch against the generations that existed before
  it, then apply that batch's Parse/Bind/Close operations in wire order.
- A portal retains its Bind-time generation. Replacing or closing the statement
  name must not change an already bound portal. Clear portals at the transaction
  boundary reported by PostgreSQL.
- A successful Sync can acknowledge the complete cycle. On an ErrorResponse,
  either reconcile individual acknowledgments or invalidate affected identities;
  guessing that every pending operation succeeded or that none succeeded is unsafe.
- Replay entries must retain their actual Parse dependencies, within the replay
  byte budget. Looking them up from the latest registry during recovery can replay
  different SQL after a Close/redefine or a failed Parse.
- Restore on a fresh connection or verify exact prepared generations already on
  it. A set containing only statement names cannot establish generation equality.

Acceptance must include rejected duplicate Parse, Close/redefine, Bind before
redefinition, and cross-cycle Execute with binary parameters. Faults before send
must not re-prepare the wrong generation merely because the request itself is
known to be unsent.
