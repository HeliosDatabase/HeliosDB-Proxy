# HeliosProxy — handover and recommended order of work

**Date:** 2026-09-11 · **From:** the Proxy session on gpc001ca (closing) · **Repo:**
`HeliosDatabase/HeliosDB-Proxy`, main at `cea5b3a` · **Released:** 1.7.0 (crates.io,
tag `v1.7.0`)

Everything below is already reflected in the repo and in GitHub issues. This file adds
the one thing those cannot: the order I would work in, and why.

---

## Where things stand

**Transaction Replay is correctness-complete.** The September 2026 audit found six
defects in it. TR-01/TR-02/TR-05 shipped in 1.6.1; TR-03/TR-04/TR-06 and H-07 shipped in
1.7.0. Replay now verifies its own results against a digest of what the client already
saw, refuses what it cannot reproduce (snapshot-pinned transactions, unverifiable
responses, opaque reads), restores session state transactionally, and runs the whole
recovery under one `write_timeout_secs` deadline.

**Docs and site are truthed.** Every TR reference in the repo was corrected — the docs
had been claiming cursor restore and prepared-statement restore, neither of which
happens, while hiding that in-session replay is core and needs no feature flag. The
website carries the same correction (`Website@d10fccd`) and the 1.7.0 release post is
live as blog id 42.

**Downstream:** `../Lite` is pinned to `=1.7.0` and pushed.

## Recommended order

### 1. O-01 — `migration_ready` masks apply errors · [#44] · P0 · small

`mirror::status` subtracts apply errors out of the lag and then decides readiness from
that lag, so failed mirrored writes cancel themselves out and `/api/migration/status`
reports the target safe to cut over while writes are missing. It is a few lines to fix
and a test to add, and it is the only open item where the failure mode is *silent data
loss during a migration a human explicitly asked to be told about*. Do it first because
it is cheap, not because it is hard.

### 2. TR-07 — journal and operator replay tooling · [#49] · P1 · large

The last open item in the Transaction Replay group, and the only place where the product
still describes something as more durable than it is: the `ha-tr` journal is post-response
SQL text in process memory, not a WAL, and `/api/replay` is built on it. Finishing it
closes the group cleanly while the context is fresh — the lexer, the delivery
classification and the harnesses it needs all exist now.

### 3. H-01 + H-02 — authoritative topology, then quorum and fencing · [#52] [#53] · P0 · large

The audit's own delivery sequence puts the HA contracts next, and they are a pair: a
routing snapshot with a leader identity and authority epoch (H-01) is meaningless without
lease expiry and fencing to back it (H-02). Today the daemon picks the first reachable
node whose `role = "primary"` health check passes, which is not an authority model.

One thing to carry into the design rather than discover late: a proxy-side epoch cannot
fence clients that connect around the proxy. Split-brain prevention has to be enforced by
the database or by exclusive network/backend control. Write that limit into the docs at
the same time as the code.

### 4. C-02 — commit-aware cache invalidation · in [#54] · P0 · medium

The highest-priority item not yet filed as its own issue. Every result-cache tier
invalidates on write observation rather than on commit, so a rolled-back write can evict
and an unobserved commit can leave stale entries. File it as an issue when work starts.

### 5. Interleave the cheap ones · [#45] [#46] · P1 · small each

O-02 (`BackendConfig.query_timeout` is set by every caller and read by none —
`run_query` hardcodes 30s) is an afternoon and removes a gate-5 violation. O-03 (shadow
execution buffers both result sets unbounded and runs sequentially despite a doc comment
promising concurrency) is slightly larger. Both are good filler between the big items.

### 6. Later · [#47] [#48] [#50] [#51] and the rest of [#54]

O-04, O-05, TR-08, TR-09 are P2/P3 and none of them is a correctness risk. TR-08 and
TR-09 are availability improvements on paths that already refuse safely.

## Process rules that are not optional in this environment

These caused real incidents; they are in `CLAUDE.md` in the repo but worth repeating.

- **One heavy job at a time, always bounded.** Every `cargo build|test|bench` runs as
  `flock /home/gpc/HDB/sprint/coordination/build.lock systemd-run --user --scope --collect
  -q -p MemoryMax=24G -p MemorySwapMax=0 <cmd>`. A runaway benchmark (38 GiB RSS) once
  livelocked this host for 16 hours. Never run matrix profiles in parallel.
- **Use your own `CARGO_TARGET_DIR`** when working in a second worktree. Sharing one
  across worktrees poisons freshness and produces gate results that are not about your
  tree.
- **The full gate before any merge or release:** `cargo fmt --check`; `clippy -D warnings`
  on default, `ha-tr`, `all-features`, `all-features,postgres-topology`; `cargo test` on
  the same four; `cargo +1.86 check --locked --features msrv-features`; bench compile;
  `--no-default-features` check. At 1.7.0 that was 432 / 518 / 1726 / 1727 tests.
- **Gate 5 — no hardcoded thresholds.** Every new timeout, size or limit must be a
  `proxy.toml` key with a serde default, a `validate()` rule, a drift test, and an entry
  in both `config/proxy.full.toml` and `docs/configuration.md`.
- **Do not touch** `/home/gpc/heliosdb-ada-data`, any `/data` directory, or running
  heliosdb services and containers. The deployed Nano at `100.64.0.2:54320` is a
  protected standby, not a test target.
- **Releases** bump `Cargo.toml` + `Cargo.lock` + `CHANGELOG.md`, tag `vX.Y.Z`, and the
  tag push triggers `crates-io.yml`. Then bump the exact `heliosdb-proxy` pin in
  `../Lite/Cargo.toml` **and** the one `version =` line in `../Lite/Cargo.lock` — editing
  the lock by hand avoids the unrelated resolver churn a `cargo update --offline`
  introduces. Skipping the pin breaks every cargo command in Lite.

## Test assets worth knowing about

- `tests/integration/tr_commit_outcome.py` — starts its own PostgreSQL 18.4 container;
  `--suite commit` (7 cases) destroys the connection with a `COMMIT` in flight and checks
  the client's report against the database's real state; `--suite stream` (13 cases) does
  the same for partially delivered results. These found the defects 1.6.1 and 1.7.0 fixed.
- `scripts/regress/tr-boundary-test.py` — 26 synthetic commit-boundary cases, no backend
  needed, seconds to run. Run it on any change to `replay_sql.rs` or the classifier.
- `scripts/regress/run.sh` (BK=pg) — the broad live battery; needs an already-running
  PG 18.4 at `127.0.0.1:25433`. It does not start one.
- **Criterion benches do not link the changed relay path.** `benches/pooling.rs` and
  `benches/routing.rs` are pooling/routing microbenchmarks; a byte-identical-binary
  control confirmed they do not exercise the daemon code TR changes touch. Do not read a
  bench delta as a verdict on a replay change, and do not claim a bench gate you did not
  run.
